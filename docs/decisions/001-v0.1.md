# ADR 001 — Mars v0.1: loop mínimo y límites explícitos

Estado: aceptado para el prototipo 0.1. Fecha: 2026-09-08.

## Alcance

Se implementa la sección 36 y el circuito de autenticación necesario para probar proveedores reales. Core, providers, auth, runtime, tools, SDK y CLI tienen código funcional; no se crean paquetes vacíos para el roadmap. Las APIs internas son privadas y provisionales.

## Opciones consideradas

| Decisión | Opciones | Elegida y motivo |
| --- | --- | --- |
| CLI | Node `parseArgs` + readline / Commander / framework TUI | Node: pocos flags y comandos, ninguna dependencia de interfaz en core. |
| Validación/JSON Schema | validación manual / Zod / TypeBox + Ajv | Zod 4: una definición produce validación runtime y JSON Schema; objetos estrictos, sin mantener dos contratos. |
| Build | `tsc` / esbuild / tsup | `tsc`: chequeo estricto y emisión ESM/declaraciones; no necesitamos bundling. |
| Tests | `node:test` / Vitest / Jest | Node: fake provider y fetch inyectable cubren los límites sin mocks de framework. |
| Logging/eventos | callback tipado / EventEmitter / Pino | Callback tipado: eventos estructurados sin persistencia ni logs de argumentos, resultados o claves. |
| Adaptador real | SDK oficial OpenAI / fetch y parser SSE propios | SDK oficial: transporte, SSE y tipos mantenidos; traducción al IR dentro del adapter. |
| API OpenAI | Chat Completions / Codex SDK | OpenAI API usa Chat Completions; la suscripción de ChatGPT usa el SDK/runtime oficial de Codex. |
| Credenciales | entorno + memoria / keychain / JSON local | Entorno y `CredentialStore`; `auto` usa `keytar` si está disponible y `file` ofrece fallback atómico explícito. Los providers no conocen el backend. |
| Sesiones | memoria / JSONL / SQLite | JSON atómico por workspace para permitir resume sin introducir SQLite. |
| Workspace | prefijos de texto / rutas y lstat / sandbox SO | `relative`, canonical root y `lstat`; se rechazan todos los enlaces para reducir ambigüedad. Docker queda como aislamiento opt-in y el host sigue explícito. |

No se añade una librería OAuth: PKCE y device code son pequeños, inyectables y testeables con `fetch` estándar. No se realizan reintentos automáticos: repetir un stream después de ejecutar una tool puede duplicar efectos. El SDK oficial también lleva `maxRetries: 0`.

## Flujo y garantías

CLI → SDK → core loop → provider → tool call → schema → permisos/ruta → ejecución → observación correlacionada → provider → final.

El modelo nunca ejecuta directamente. Las tools reciben argumentos validados y señal de cancelación. Cada llamada tiene un ID no reutilizado en la sesión. Se comprueban los límites antes de ejecutar nuevas tools. Un stream cortado, una cancelación o el agotamiento de turnos no se presentan como respuesta final exitosa.

Las escrituras utilizan temporal exclusivo + rename para evitar truncar el destino ante un fallo previo al reemplazo. No se promete durabilidad ante pérdida de alimentación. No hay rollback de shell o de escrituras ya terminadas si una llamada posterior falla. El checkpoint en memoria conserva resultados previos y marca las llamadas pendientes como inciertas.

La sesión impide ejecuciones concurrentes en la misma instancia. Cada instancia es independiente; no hay locking entre procesos. Los adapters deben cooperar con AbortSignal. El core limita la espera, pero no puede detener código arbitrario que ignore la cancelación.

## Shell y filesystem

En v0.1 los archivos tienen límites de aplicación y shell requiere aprobación explícita; el modo host no aísla el proceso. Se considera y se descarta una denylist de substrings para comandos: es trivial evadirla. La clasificación extensible de operaciones destructivas pertenece a 0.3. El modo Docker opt-in ofrece contención práctica con mount explícito y red desactivada, pero requiere una imagen confiable y Docker operativo.

Se filtran variables de entorno con allowlist, se utiliza PowerShell sin perfiles/bash sin scripts de inicio, y la terminación usa `taskkill /T /F` en Windows o grupo de procesos en POSIX. Los procesos deliberadamente separados y carreras de filesystem requieren aislamiento del SO. El código no afirma resolverlos.

## Distribución y verificación

Un único build preserva la estructura de carpetas en `dist`; los imports relativos mantienen los límites entre módulos sin publicar paquetes internos. El root proporciona bin y exports de SDK; permanece `private: true` hasta preparar una release. Node 24 y lockfile pnpm fijan una base reproducible.

Tests del loop con fake provider antes de integrar el adapter; luego contratos SSE/errores, archivos y shell reales y CLI compilada. CI declara Windows, Ubuntu y macOS; el resultado remoto solo se conocerá cuando se ejecute en GitHub.
