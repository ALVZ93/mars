# Auditoría funcional de MARS — 2026-10-11

Alcance: CLI, SDK, loop, proveedores, permisos, persistencia, MCP, sandbox y distribución. La referencia es el comportamiento del código y las pruebas ejecutadas localmente, no los checks históricos del handoff.

## Contratos de corrección

- Búsqueda y lectura deben aplicar la misma frontera de workspace y secretos; Git de inspección no debe ejecutar helpers ni mostrar diffs de archivos bloqueados.
- `gitCommit` y `gitPush` deben participar también en los comandos shell reconocibles. El clasificador de shell es heurístico; el modo host no ofrece aislamiento contra código arbitrario.
- Cancelar checks debe propagar cancelación; un check fallido debe producir código de salida no cero también con `--json`.
- Solo una operación puede modificar una sesión a la vez, incluida toda la ejecución de un workflow y sus checks.
- Las fases declaradas de lectura solo pueden ejecutar sus herramientas permitidas, aunque el modelo solicite otras.
- Un workflow no puede declarar verificación sin haber ejecutado checks; los formatos persistidos deben rechazar versiones futuras desconocidas.
- Gemini debe enviar instrucciones con el campo oficial, conservar correlación entre tool calls, procesar SSE fragmentado y rechazar respuestas truncadas.
- Codex solo puede reutilizar un hilo si modelo, herramientas e historial enviado siguen coincidiendo.
- MCP debe drenar stderr, acotar mensajes, limpiar recursos y permitir reconexión explícita.

## Línea base

`pnpm test`: 75/75 tests aprobados en Windows, Node 24.11.1. La suite verde no detectaba los casos anteriores. pnpm instalado: 11.25.0; manifiesto: 11.19.0.

## Hallazgos corregidos

Prioridades: P0 expone datos o rompe una frontera fundamental; P1 rompe el funcionamiento o su diagnóstico; P2 afecta continuidad, precisión o experiencia. Son prioridades de esta auditoría, no una clasificación de vulnerabilidades certificada.

| Prioridad | Hallazgo reproducible | Corrección | Evidencia |
| --- | --- | --- | --- |
| P0 | Buscar desde `.` recorría `.aws`, `.ssh`, `.azure` y `.config`, aunque `read_file` los bloqueaba | Validar cada ruta con `Workspace.resolve`; lectura limitada por handle sin seguir enlaces | `audit.test.mjs`: búsqueda recursiva de marcador sensible |
| P0 | `git diff` sin path podía enviar contenido de `.env` y otros archivos bloqueados al modelo | Exclusiones Git de rutas sensibles; desactivar external diff, textconv y fsmonitor | Diff real en repositorio temporal con secretos y archivo público |
| P1 | `permissions.gitCommit/gitPush` no participaban en `shell` | Comprobar políticas para comandos Git reconocibles antes de ejecutar | Commit, push, `git -C` y `git.exe` denegados con shell/red permitidas |
| P1 | Las fases declaradas read-only podían ejecutar `write_file`, shell o MCP | `allowedTools` en fases y executor efectivo que deniega llamadas no permitidas | Un proveedor intenta escribir durante review; el archivo no aparece |
| P1 | El bloqueo se liberaba entre fases y durante los checks de workflows | Exclusión de la operación completa; sesiones activas hasta finalizar | Segundo run rechazado mientras el check está bloqueado |
| P1 | `check --json` devolvía exit 0 incluso con `verified: false` | Mantener JSON válido y devolver exit 1 | Proceso CLI real |
| P1 | Checks podían convertir cancelación en un fallo normal | Propagar señal antes y después del executor y en errores | Executor cancelado devuelve `CancelledError` |
| P1 | Una verificación fallida dejaba la sesión marcada como completada | Persistir failed/cancelled y completar solo al terminar todos los checks | Sesión JSON releída después del fallo |
| P1 | Workflows personalizados sin checks registraban verificación positiva | Registrar `verificationPassed` solo después de checks reales y vigentes | Workflow sin fase de verificación |
| P1 | Gemini enviaba `system` en lugar de `systemInstruction` | Corregir contrato REST | Inspección de body de transporte |
| P1 | Gemini reutilizaba IDs como `read_file-1` entre turnos, que el loop rechaza | IDs únicos por llamada | Dos respuestas de transporte con la misma herramienta |
| P1 | Parsers SSE de Gemini/Anthropic fallaban con CRLF fragmentado | Parser compartido con UTF-8 incremental y límites por frame y respuesta | Stream fragmentado en bloques de tres bytes |
| P1 | Gemini aceptaba respuestas sin finish reason; Anthropic aceptaba `max_tokens` | Rechazar streams incompletos y respuestas truncadas | STOP, ausencia de STOP, MAX_TOKENS, SAFETY y max_tokens |
| P1 | Codex reutilizaba hilos tras cambiar modelo, tools o prefijo del historial | Comparar hashes del contexto enviado y configuración | Hilos reiniciados ante cada cambio; regresión previa mantiene reutilización válida |
| P1 | OpenAI solicitaba strict incluso con esquemas MCP opcionales incompatibles | Solicitar strict solo cuando el esquema cumple sus restricciones estructurales | Payload con propiedades opcionales; schemas built-in conservan strict |
| P1 | MCP podía bloquearse al llenarse stderr y solo descubría la primera página | Drenar stderr y paginar con límites y detección de ciclos | Servidor real con 2 MB de stderr y dos páginas |
| P1 | MCP conservaba el arranque cacheado tras cerrar y acumulaba mensajes sin límite | Reiniciar estado; limitar mensajes; tratar errores de stdin | Reconexión y respuesta oversized en procesos separados |
| P1 | `resume` sin TTY podía entrar en un bucle de input vacío | Fallar inmediatamente con diagnóstico de terminal | CLI real con stdin/stdout redirigidos |
| P1 | Fallos asíncronos del store podían provocar rechazo sin manejar durante el modelo | Cola que captura errores y los comunica al hacer flush | Store ENOSPC durante un turno lento |
| P1 | Anthropic estaba bloqueado solo en CLI: el adapter aún llevaba client ID y flujo OAuth heredados | Eliminar flujo/client ID; bloquear login y refresh también en adapter y rechazar credenciales OAuth en CLI | Login/refresh no hacen solicitudes; credenciales guardadas no evitan la política |
| P1 | OAuth Kimi guardado funcionaba sin el opt-in experimental posterior | Exigir flag también al crear el provider | Credencial persistida denegada sin flag |
| P1 | Logout Gemini con API key exigía `MARS_GEMINI_CLIENT_ID` | No construir el adapter OAuth para eliminar API keys | Logout sin cliente OAuth |
| P2 | Routing explícito/configurado saltaba filtros; contexto desconocido se trataba como infinito | Aplicar restricciones conocidas también a targets seleccionados; rechazar capacidades/contexto desconocidos cuando se requieren | Filtros de proveedor/contexto en ambas rutas |
| P2 | Formatos de sesión/configuración no tenían versión | Escribir versión 1, aceptar formato anterior y rechazar versiones desconocidas | Roundtrip y formato futuro 999 |
| P2 | Un cambio de modelo fallido cerraba la sesión interactiva utilizable | Crear reemplazo antes de cerrar; restaurar terminal en finally | Prueba manual en PTY: target inválido seguido de tarea fake correcta |
| P2 | Credenciales explícitas consultaban primero un store roto; claves vacías podían persistirse | Resolver explícitas antes y validar al escribir | Store que lanza error no participa en resolución explícita |
| P2 | Errores Anthropic podían reflejar API keys en su diagnóstico | Redactar secretos conocidos | Respuesta HTTP que incluye la clave fixture |
| P2 | Solo se hacía checkpoint al terminar toda la ejecución | Encolar checkpoint tras cada turno completo; limpiar temporizadores de retry | Checkpoint observado antes de la siguiente petición |
| P2 | Docker aceptaba cwd `..`, una imagen que comenzaba con flags y no eliminaba el contenedor al cancelar cliente | Validación previa; nombre único y cleanup explícito | Negativos de cwd/imagen; cleanup de contenedor aún requiere Docker real |
| P2 | Instrucciones y raíces de skills se duplicaban por un rename anterior | Eliminar duplicados; respetar precedencia entorno sobre config al iniciar CLI | Suite de contexto/skills y revisión de código |

La política de shell es un clasificador heurístico: las pruebas de Git no demuestran que pueda bloquear commits ocultos dentro de scripts o programas arbitrarios. La frontera de permisos de archivos tampoco elimina carreras contra procesos externos host que alteren directorios concurrentemente.

## Cobertura por subsistema y trabajo restante

| Área | Estado después de las correcciones | Pendiente concreto |
| --- | --- | --- |
| Core y SDK | Loop, límites, retries, cancelación, checkpoints, compaction y exclusión verificados offline | Un límite en caracteres no equivale al límite real de tokens del modelo; recuperación ante caída abrupta no garantiza fsync ni checkpoints transaccionales de efectos externos |
| Herramientas/permisos | Lectura/escritura, búsqueda y Git cubiertos por positivos/negativos; checks usan executor y permisos comunes | Host sigue ejecutando código con autoridad del usuario; scripts aprobados pueden ejecutar red, Git o acciones destructivas indirectamente |
| Sesiones/config | Atomic rename, cola, errores de disco y versión verificadas | Dos procesos independientes sobre el mismo archivo no tienen lock entre procesos; no compartir una sesión simultáneamente entre CLIs |
| CLI | Flujos offline, JSON, resume y recuperación de cambio de modelo cubiertos | `2B-F01`: estado global Codex y marcador local pueden discrepar; `/model` con `--no-save` crea conversación nueva por diseño |
| Proveedores | OpenAI, Codex, Anthropic/Kimi, Gemini y Qwen tienen pruebas de transporte | Falta repetir login, refresh, logout, rate limits y múltiples tool calls con cuentas reales después de estos cambios; catálogo estático y permisos de modelos no se descubren remotamente |
| Auth nativa | Factory estricta y adapters tienen pruebas de contrato con fixtures | No se ha comprobado un roundtrip real del llavero en cada SO; OAuth Gemini depende del cliente Cloud propio; logout local no implica revocar una API key en el proveedor |
| MCP | Procesos stdio reales, paginación, reconexión, cancelación y límites | Subconjunto JSON Schema, sin resources/prompts ni transports HTTP; servidores son procesos de confianza y no comparten sandbox Docker de shell |
| Docker | Selección y checks comunes; validación negativa y cleanup implementado | Motor ausente aquí. Validar cancelación/contenedor, montaje y permisos en Windows/macOS/Linux; imagen por defecto no incluye todos los toolchains/pnpm del usuario |
| Routing | Selección determinista y filtros corregidos; informes por run añadidos en la entrega posterior | Salud no interviene en selección; sin historial por modelo, presupuesto/coste ni fallback entre proveedores. `MODEL_CATALOG` no contiene context windows conocidos |
| Skills/evidencia | Precedencia, selección por tarea y contadores locales | Los contadores reflejan ejecución del runtime; no prueban corrección de una tarea. Sin promoción/evaluación automática de skills ni catálogo built-in |
| Workflows | Fases secuenciales, separación de tools y checks reales; reparación acotada opt-in añadida después de esta auditoría | Sin contrato de diff obligatorio ni revisor independiente garantizado; un check aprobado no demuestra todos los requisitos del usuario |
| Extensiones | Tools/providers/workflows y hooks síncronos existentes | SDK todavía 0.x; hooks de observación no son middleware de autorización; sin cargador de plugins ni comandos personalizados |
| Distribución/CI | Tarball local, CLI, SDK y proveedor fake comprobados; tag coincide con versión | Instalación limpia con descarga de dependencias, audit npm y CI de este diff en macOS/Linux pendientes; publicación y Trusted Publishing no se verificaron |
| Landing | Assets locales presentes y tests estructurales pasan | No se certificó accesibilidad/visual responsive ni despliegue público en esta auditoría del runtime |

El handoff incluye cinco runs reales históricos en `docs/dogfooding/runs/`. Son evidencia previa; no sustituyen una nueva prueba de proveedores tras modificar sus transports.

## Verificación de esta revisión

- Línea base: 75 tests. Suite final `pnpm test`: **97/97 aprobados**, cero fallos, cancelaciones o skips; build TypeScript correcto. Duración final: 31,85 s, Windows/Node 24.11.1.
- Entrega posterior del mismo día: reparación acotada e informes de ejecución, con 15 pruebas nuevas en `tests/value.test.mjs`; **112/112 tests aprobados**, build correcto, duración 46,37 s. Contrato en [ADR 005](decisions/005-verification-repair-and-reports.md) y comparación funcional en [ventajas del harness](ventajas-del-harness.md).
- Steering posterior: memoria revisada y captura local de procedimientos, recibos persistidos e integración CLI/SDK; **122/122 tests aprobados**, build correcto, duración 55,75 s. Diez tests nuevos de conocimiento; alcance y límites en [dirección de producto](direccion-producto.md) y [ADR 006](decisions/006-reviewed-project-knowledge.md).
- **22 regresiones nuevas** en `tests/audit.test.mjs`; pruebas existentes de transporte actualizadas para rechazar el login Anthropic y exigir cierre válido de Gemini.
- Tarball offline: **111 archivos**, binario `--version`, exports públicos y tarea fake correctos. Artefacto: `.release-test/audit-Pwtn0Q/alvz93-mars-0.1.0.tgz`. Resolvió dependencias desde la instalación del workspace: **no equivale a una instalación limpia**.
- PTY Windows: `/model invalid-provider:x` produce error; una tarea posterior sigue leyendo el fixture con fake en la misma sesión.
- `node scripts/verify-release.mjs v0.1.0`: correcto. `git diff --check`: sin errores.
- Docker CLI presente; API del motor `docker_engine` no disponible. No se ejecutaron contenedores.
- `pnpm audit --prod`: consulta no completada. La revisión automática rechazó exportar metadatos al registro npm; autorización solicitada y pendiente.
- `pnpm test:package`: primer intento bloqueado por permisos de caché del usuario; segundo con caché local quedó esperando red y fue cancelado. Se sustituyó únicamente la comprobación de contenido/ejecución local del tarball, sin eludir la autorización de red.

Logs locales conservados en `.release-test/audit-results-9d2b9686-0947-41f2-a5a6-08e75af8d994/` (ignorados por Git). La comprobación offline se puede repetir con `node .release-test/audit-package.mjs`, usando las dependencias ya instaladas.

## Criterio de cierre hacia una release

1. Instalar el tarball y ejecutar la matriz Windows/macOS/Linux sobre este diff; comprobar llavero nativo y módulos opcionales.
2. Ejecutar `pnpm audit --prod` con autorización de registro y resolver hallazgos si los hubiera.
3. Repetir tareas reales con tool calls, cancelación y resume en los proveedores anunciados. Registrar consumos, fallos y resultados sin marcar una respuesta textual como tarea verificada.
4. Con Docker disponible, probar que la cancelación elimina el contenedor y que checks se ejecutan dentro de la imagen elegida; documentar toolchains soportados.
5. Resolver `2B-F01`, confirmar el catálogo disponible para las cuentas usadas y actualizar matriz/release con esa evidencia.
6. Verificar configuración npm/Trusted Publishing antes de publicar; no se ha realizado publicación ni push durante esta auditoría.

El runtime queda más cerca de ser utilizable con garantías comprobables. No hay base para asignar un porcentaje honesto de «100 % funcional» mientras falten los gates externos anteriores.
